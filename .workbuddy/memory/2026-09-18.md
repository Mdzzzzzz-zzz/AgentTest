`manifest` 缺 `assetbundle` → `AssetBundle` 类型不存在 → `WXBase.cs:884` CS0103 → 无 `Wx.dll`
→ 无 `WxEditor.dll`（asmdef 引用 `Wx`）→ `WeixinSubTargetManager` 的 `[InitializeOnLoad]` **从未执行**
→ `MiniGameSubplatformManager.RegisterSubplatform()` 从未调用 → **Subtarget 下拉里根本不存在 `WeChat:微信小游戏`**
→ 只剩引擎内置「微信小游戏」→ 走 `DefaultWeChatMiniGameSettings.ApplySettings`（硬编码插件模式路径，已在 `UnityEditor.CoreModule.dll` 内证实含
`Assets/WX-WASM-SDK-V2/Editor/MiniGameConfig.asset`）→ 文件不存在返回 null → `FromJsonOverwrite(json, null)` → `ArgumentNullException`。

**由此得出一个必须写进手册的顺序陷阱**：装回模块**之前**，下拉里不会出现 `WeChat:微信小游戏`，
**选项出现本身就是修复生效的第一个信号**。正确顺序 = ①装 `com.unity.modules.assetbundle` → ②等重编译并确认 `Wx.dll`/`WxEditor.dll` 产出 → ③下拉这时才出现该选项，选它 → ④填非空 BuildPath → Build。

**教训（第二次同类）**：我又一次把「同时出现的两个报错」默认当成两条独立故障。
**多个报错同时出现 ≠ 多个根因**；汇编产出物（`Library/ScriptAssemblies/`）的存在/缺失是判断"编译是否真的成功"最快的硬证据，应先查它再下结论。

**仍未对齐的一处**：`MiniGameProfile.asset` 的 PlayerSettings 段记录了 `weixinMiniGameTemplate: PATH:...PackageCache\com.qq.weixin.minigame@a09d4b29da\WebGLTemplates\WXTemplate2022TJ`，
而这正是 `WeixinSubplatformInterface.WechatBuildPreprocess:218-220` 才会写入的路径。既然 `WxEditor` 从未编译，这个值来源存疑，
已回退给 engineering-lead 判定（内置 helper 自解析 / 早前残留），不自行编造解释。

### A1-UNBLOCK-03 回传：`assetbundle` 是**唯一**缺失且必需的引擎模块（无打地鼠风险）

engineering-lead-2 只读审计结论（证据留在 `D:\NewOne\Temp\dll_*.txt`）：

- **`com.unity.modules.assetbundle`＝必需且当前缺失**。两处证据：`Runtime/WXBase.cs:884` 的 `AssetBundle.LoadFromMemory`；
  以及随包插件 `Unity.FontABTool.dll` 内含类型 `AssetBundle`（该插件在 `WXBase.cs:881` `GetWXFont` 里被调用）。
  ⇒ **不只是托管侧编译期硬失败，IL2CPP 原生侧也必须有这个模块**，无法靠改代码绕过。
- 其余候选（VideoPlayer / ParticleSystem / Terrain / NavMesh / Cloth / Tilemap / AudioClip / EncodeToPNG）在 SDK 源码中**均无类型引用**。
- `unitywebrequest`、`ugui` 已满足（`WXBase` 用的是插件 dll 内的 `UnityWebRequest`；`Runtime/WXTouchInputOverride.cs:5,7` 直引 `EventSystems`/`UI`）；`jsonserialize` 已满足。

⚠️ **防御性发现（值得记住）**：`unitywebrequest` / `video` / `ugui` 目前**只是经 `cn.tuanjie.ai.generators`、`cn.tuanjie.codely.bridge` 传递引入**，manifest 并未显式声明。
⇒ **一旦为了瘦包移除这两个 codey 桥包，SDK 会在 IL2CPP 阶段断链。** 建议在 manifest 显式声明这几项作为保险（显式声明不改变已有产物体积，因为模块本来就已经在）。

**通用教训（第三条）**：`packages-lock.json` 里出现某模块 ≠ manifest 声明了它 —— 传递依赖会在上游包被移除时静默消失。
判断「这个模块到底靠什么在」要区分 `depth: 0`（显式）与 `depth: 1+`（传递）。

### A1-UNBLOCK-02 追加回传：残留值判定为 (b)，并厘清事故时序

engineering-lead 独立复现了 `ScriptAssemblies`（38 个文件，无 `Wx.dll`/`WxEditor.dll`，其余齐全）⇒ 连坐链**实锤**。

**残留值 `weixinMiniGameTemplate: PATH:...WXTemplate2022TJ` 判定 = (b) 更早某次 `WxEditor` 可编译时写入的残留，证据强度：强。**
证伪 (a) 的依据：`WXTemplate2022TJ` 字面量在这些地方**全 0 命中** —— `UnityEditor.CoreModule.dll`（UTF-16）、Extensions DLL、
WeixinMiniGame BuildProgram exe、模块 `Managed/` 下 142 个 DLL、SDK 预编译 `wx-editor.dll`；
它只存在于 SDK 包的**目录名**与 SDK **源码** `WeixinSubplatformInterface.cs:218`（唯一写 `PATH:{abs}` 的代码）⇒ 引擎内置 helper 造不出这个值。

**由此厘清事故时序（重要）**：既然曾有一次 `WxEditor` 能编译，说明
**`assetbundle` 模块是在「SDK 已装好 + profile 已配好」之后才被裁掉的** —— 即这次事故是**压体积步骤自己造成的**。
⇒ **行为准则：任何为压体积而做的模块裁剪，必须紧接一次「转换 SDK 能否编译」的验证**（判据：`Library/ScriptAssemblies/` 下是否有 `Wx.dll` + `WxEditor.dll`）。
⇒ **第二条准则：profile 里看起来配好了（模板路径对、字段齐全）≠ SDK 可用**；唯一可信信号是程序集产出物。

**修正一条我先前的错误判断**：我曾把 profile 里 `DefaultWeChatMiniGameSettings` 当作「用户选错了子平台」的证据。
更准确的表述是：用户**没有选错**，是 SDK 的子平台**当时根本没注册进下拉**（因 `WxEditor` 编不出来）。
「下拉里没有 SDK 选项」与「用户选错了选项」表象相同、根因完全不同 —— 不要据此推断用户操作有误。
