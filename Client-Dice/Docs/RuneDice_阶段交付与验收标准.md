# Rune Dice 阶段交付与验收标准

> 目标工程：`D:\NewOne\Client-Dice`
>
> 本文是阶段完成度的唯一验收口径。功能清单用于跟踪工作量，本文件用于判断某个阶段能否签收。
>
> 版本：v0.1

## 1. 阶段签收规则

一个阶段只有同时满足以下条件才标记为“已完成”：

1. 该阶段的所有硬性交付物齐全。
2. 所有 P0 验收用例通过。
3. 没有阻塞主流程、破坏存档或导致数据错误的缺陷。
4. 团结引擎 Console 无 Error，Windows x64 构建成功。
5. 用户根据本文件完成测试并明确签收。

我完成开发和自测后，只能把阶段标记为“待验收”，不能自行标记为“已完成”。如果存在允许遗留的问题，必须写进阶段的 `KnownIssues.md`，由用户决定是否接受。

### 1.1 缺陷级别

| 级别 | 定义 | 阶段能否签收 |
|---|---|---|
| S0 阻断 | 无法启动、崩溃、无法继续主流程、存档损坏 | 不能 |
| S1 严重 | 核心规则错误、结算重复、胜负错误、必现卡死 | 不能 |
| S2 一般 | 非核心功能异常，有明确规避方式 | 用户决定 |
| S3 轻微 | 文案、轻微视觉、偶发不影响流程的问题 | 可以，必须记录 |

### 1.2 每阶段固定交付包

每个阶段交付时都必须包含：

```text
D:\NewOne\Client-Dice
├─ Assets/                         可编辑工程内容
├─ Packages/                       锁定的包依赖
├─ ProjectSettings/                团结引擎工程配置
├─ Builds/<阶段>/Windows/          可直接运行的 Windows x64 包
└─ Docs/Delivery/<阶段>/
   ├─ CHANGELOG.md                 本阶段新增、修改、删除的功能
   ├─ TEST-REPORT.md               自动测试与人工自测结果
   └─ KnownIssues.md               已知问题、影响、规避方式
```

可运行包的主菜单或屏幕角落必须显示版本，例如 `M1.0.0`。测试反馈必须带阶段版本，避免把旧包的问题记到新包。

### 1.3 通用构建验收

以下用例适用于 M1～M4：

| ID | 测试步骤 | 通过标准 |
|---|---|---|
| COMMON-01 | 直接运行交付目录内的 EXE | 进入游戏，无缺 DLL、崩溃或黑屏 |
| COMMON-02 | 以 1920×1080 运行 10 分钟 | 主流程无未处理异常，UI 无关键遮挡 |
| COMMON-03 | 连续执行阶段核心流程 3 次 | 结果稳定，不出现对象或状态残留 |
| COMMON-04 | 查看团结引擎 Console 和 Player 日志 | 无 Error；允许的 Warning 已记入 KnownIssues |
| COMMON-05 | 在主流程各界面按下退出/返回 | 不会卡死、重复结算或留下不可关闭弹窗 |
| COMMON-06 | 关闭后重新启动游戏 | 配置和该阶段要求保存的数据正确恢复 |

## 2. 验收模式

从 M1 开始，开发包必须提供“验收模式”。正式发布时可以通过编译宏关闭。入口放在主界面右下角或按 `F10` 打开。

验收模式至少提供：

- 显示版本号、随机种子、当前场景和当前战斗阶段。
- 选择固定验收场景。
- 设置玩家生命、护盾和金币。
- 生成指定类型、等级和位置的骰子。
- 设置敌人生命并选择下一行动。
- 查看合并队列和当前活动骰子数。
- 1×/2×/3×表现速度。
- 清空存档和复制日志路径。

验收模式造成的存档必须带 `Debug` 标记，不能污染正常游戏存档。

## 3. M0：物理合并原型

### 3.1 交付目标

交付一个可以独立运行的物理玩具，证明当前资源、团结引擎版本、骰子碰撞和升级表现能够正常工作。M0 不包含正式战斗规则。

### 3.2 硬性交付物

- 团结引擎 1.10.2 可打开的工程。
- Windows x64 可运行包。
- Rune Dice 背景、Logo、1～6 级骰子贴图。
- 点击和空格投放骰子。
- 相同等级骰子碰撞合并。
- 分数、Combo、重开。

### 3.3 用户验收用例

| ID | 测试步骤 | 通过标准 |
|---|---|---|
| M0-01 | 运行 `Build/DiceMergeDemo.exe` | 5 秒内进入 Demo，无黑屏或崩溃 |
| M0-02 | 在场地不同位置点击 10 次 | 每次合法点击只生成一枚骰子 |
| M0-03 | 连续按空格 10 次 | 骰子从上方生成并参与物理碰撞 |
| M0-04 | 让两个同级骰子发生碰撞 | 两枚原骰只合并一次，生成高一级骰 |
| M0-05 | 制造连续合并 | 分数增加并显示 Combo |
| M0-06 | 按 `R` 或点击 Restart | 清空现有骰子并恢复初始局面 |
| M0-07 | 持续操作 10 分钟 | 无崩溃、卡死或骰子穿出边界后无限下落 |

### 3.4 完成判定

- M0-01～M0-07 全部通过。
- 允许存在物理手感和平衡问题，因为这些属于 M1 重构范围。
- 当前状态：**待用户验收**。

## 4. M1：战斗垂直切片

### 4.1 交付目标

交付一场完整、可重复游玩的战斗：玩家观察敌方意图，瞄准并投掷骰子，通过攻击、治疗和护盾骰的合并效果击败敌人，或因生命归零失败。

该阶段回答一个核心问题：**物理合并是否能支撑清晰、有决策价值的回合战斗。**

### 4.2 硬性交付物

- 一个正式战斗场景和 Windows x64 构建。
- 回合准备、玩家瞄准、投掷、物理收尾、玩家结算、敌方行动、刷新七阶段状态机。
- 攻击、治疗、护盾三种骰子，等级 1～6。
- 一名玩家角色。
- 近战哥布林和弓手两种敌人。
- 敌方意图、生命/护盾、下一枚骰子和合并队列 UI。
- 胜利、失败、重新挑战。
- F10 验收模式。
- 合并、效果公式和状态机自动测试。

### 4.3 固定验收场景

| 场景 | 固定条件 | 目的 |
|---|---|---|
| M1-A 基础攻击 | 玩家 60 HP；哥布林 30 HP；场上两个 D1 攻击骰 | 验证合并、入队、伤害 |
| M1-B 治疗上限 | 玩家 55/60 HP；场上两个 D2 治疗骰 | 验证有效治疗不溢出 |
| M1-C 护盾吸收 | 玩家 60 HP；敌人预告 8 伤害；场上两个 D2 护盾骰 | 验证护盾优先扣除 |
| M1-D 连锁 | 预摆可以形成至少三次合并的攻击骰 | 验证 Chain 和队列顺序 |
| M1-E 胜利中断 | 敌人 1 HP，另有尚未执行动作 | 验证敌人死亡后停止敌方行动 |
| M1-F 失败中断 | 玩家 1 HP，敌人预告攻击 | 验证玩家死亡后停止回合并失败 |
| M1-G 睡眠超时 | 生成一枚持续轻微滚动的骰子 | 验证最多 4 秒后进入结算 |

### 4.4 用户验收用例

| ID | 测试步骤 | 通过标准 |
|---|---|---|
| M1-01 | 启动 M1-A，完成一次瞄准和投掷 | 松开鼠标只投掷一次；非玩家阶段不能再投 |
| M1-02 | 让两个同类型同等级骰子碰撞 | 只生成一个升级骰，并产生一条合并记录 |
| M1-03 | 让不同类型或不同等级骰子碰撞 | 不发生合并 |
| M1-04 | 完成 M1-A | 攻击效果按队列执行，敌人生命减少值与 UI 一致 |
| M1-05 | 完成 M1-B | 玩家恢复 5 HP 到 60，不超过最大生命 |
| M1-06 | 完成 M1-C | 8 点伤害先扣护盾，剩余部分才扣生命 |
| M1-07 | 完成 M1-D | 队列顺序和实际合并顺序一致，Chain 层数无跳号 |
| M1-08 | 完成 M1-E | 敌人死亡只触发一次，剩余敌方动作取消，进入胜利 |
| M1-09 | 完成 M1-F | 玩家生命归零后不再执行后续效果，进入失败 |
| M1-10 | 完成 M1-G | 物理阶段不会永久卡住，超时后安全进入结算 |
| M1-11 | 连续重新挑战并完成 10 场 | 无卡死、重复伤害、幽灵骰或上一场数据残留 |
| M1-12 | 用相同种子重复测试 3 次 | 初始骰子和敌方动作序列一致 |
| M1-13 | 查看敌方意图 | 目标、伤害/效果数值与实际执行完全一致 |
| M1-14 | 切换 1×/2×/3×表现速度 | 只改变表现等待，最终数值和顺序一致 |
| M1-15 | 运行自动测试 | 合并、效果公式、状态机测试全部通过 |

### 4.5 量化通过标准

- M1-01～M1-15 全部通过。
- 连续 10 场战斗 S0/S1 缺陷为 0。
- 压力场景执行 1000 次合并事务，重复结算和残留锁定为 0。
- 目标机器 1080p 下战斗阶段平均帧率不低于 60 FPS，最低帧率不低于 45 FPS；验收模式统计，不计场景首次加载。
- 物理收尾最长等待 4 秒。
- 团结引擎自动测试失败数为 0。

### 4.6 允许遗留

- 只有临时音效或无音乐。
- 只有一个战斗背景。
- 数值尚未最终平衡。
- 无地图、奖励、商店和存档。

## 5. M2：短局 Roguelike 闭环

### 5.1 交付目标

交付一局从“新游戏”到“Boss 胜利/角色死亡”的完整短流程。玩家能够通过地图选路、获得骰子和遗物、升级构筑，并在退出游戏后从最近节点继续。

该阶段回答：**战斗之外的选择是否能形成一局完整、值得重复游玩的成长体验。**

### 5.2 硬性交付物

- Boot、主菜单、角色确认、地图、战斗、结算流程。
- 一名可用角色和固定初始牌组。
- 8 行可复现地图，含普通战斗、宝箱、升级和 Boss。
- 骰子库、加权抽取、骰子三选一。
- 5 件可用遗物。
- 金币与基础奖励。
- 带版本号的局内 JSON 存档。
- 局内统计和最终结算界面。
- M2 验收模式，可跳转到指定节点并查看局内数据。

### 5.3 固定验收种子

交付时必须给出三个永久测试种子：

- `M2_LINEAR`：最短路线，覆盖普通战、升级、宝箱、Boss。
- `M2_BRANCH`：至少两次分叉，验证合法选路和汇合。
- `M2_SAVE`：用于节点边界存档和恢复。

种子对应的地图布局需要写入 `TEST-REPORT.md`。同版本内不能无说明变更。

### 5.4 用户验收用例

| ID | 测试步骤 | 通过标准 |
|---|---|---|
| M2-01 | 从主菜单选择新游戏 | 创建全新局，生命、金币和 8 枚初始骰正确 |
| M2-02 | 使用 `M2_LINEAR` 进入地图 | 地图共 8 行，首行是普通战，末行是 Boss |
| M2-03 | 尝试点击未连通节点 | 不允许进入；可选节点有明确高亮 |
| M2-04 | 赢得普通战 | 获得金币并进入骰子三选一，可选择或跳过 |
| M2-05 | 选择一枚奖励骰 | 骰子库数量和后续抽取池正确变化 |
| M2-06 | 跳过奖励 | 不加入骰子，并按规则获得跳过补偿 |
| M2-07 | 完成升级节点 | 只能选择合法骰子，升级后类型和数量不变 |
| M2-08 | 完成宝箱节点 | 三选一获得遗物，效果从下一合法时机生效 |
| M2-09 | 节点结算后退出并重启 | “继续游戏”恢复生命、金币、构筑、遗物和地图位置 |
| M2-10 | 战斗中强制退出后重启 | 返回该节点战斗开始前，不产生重复奖励 |
| M2-11 | 使用同一固定种子开新局 3 次 | 地图结构、节点内容和初始奖励序列一致 |
| M2-12 | 击败 Boss | 进入胜利统计，显示关键局内数据，继续存档被正确结束 |
| M2-13 | 在战斗中死亡 | 进入失败统计，不能从死亡后的状态继续 |
| M2-14 | 完成或失败后返回主菜单 | 可以再次新建游戏，无上一局数据残留 |
| M2-15 | 从新游戏到结算完整游玩一次 | 无需 F10 调试功能即可走完整流程 |

### 5.5 量化通过标准

- M2-01～M2-15 全部通过。
- 三个固定种子分别完整运行至少一次，S0/S1 缺陷为 0。
- 一局目标时长 20～35 分钟；若偏离，TEST-REPORT 必须给出原因。
- 存档往返测试 20 次，字段丢失、重复奖励和无法读取次数为 0。
- 同种子重复结果一致；玩家物理操作造成的差异除外。
- 节点加载时间目标小于 3 秒，首次启动目标小于 8 秒。

### 5.6 允许遗留

- 地图使用固定背景或简化连线。
- 只有一个角色、一个 Boss 和一个生物群系。
- 不包含商店、精英、事件、祭坛、符文和局外成长。
- UI 和音频可使用阶段性资源，但信息必须完整。

## 6. M3：构筑深度与节点扩展

### 6.1 交付目标

在 M2 闭环上交付至少三种策略明显不同、均可通关的构筑，并通过商店、精英、符文、事件和祭坛让地图决策具有风险收益。

该阶段回答：**多局游玩是否会产生不同构筑和不同决策，而不是重复同一最优路线。**

### 6.2 硬性交付物

- 商店：3 枚骰子、2 件遗物、移除骰子服务。
- 精英战斗：至少 2 种精英敌人和稳定遗物奖励。
- 符文：至少重掷、推力、修复三种，两格携带槽。
- 事件：至少 5 个，每个至少 2 个有意义的选择。
- 祭坛：至少 3 种结果，支持生命、金币或骰子代价。
- 六种完整核心骰子：攻击、治疗、护盾、毒、炸弹、金币。
- 至少 5 种普通敌人、2 种精英和 1 个 Boss。
- 遗物总量 10～15 件。
- 战斗与选择数据导出。

### 6.3 三种验收构筑

交付时必须提供三个固定种子或验收预设：

| 预设 | 核心策略 | 必须体现 |
|---|---|---|
| M3-BUILD-A 爆发连锁 | 攻击 + 炸弹 | 利用连锁快速清除多敌人 |
| M3-BUILD-B 防御消耗 | 护盾 + 治疗 + 毒 | 承受高压并通过持续伤害获胜 |
| M3-BUILD-C 经济成长 | 金币 + 商店/升级遗物 | 前期牺牲战力换取后期优势 |

### 6.4 用户验收用例

| ID | 测试步骤 | 通过标准 |
|---|---|---|
| M3-01 | 进入商店并依次测试购买、金币不足和售罄 | 扣款、库存、按钮状态和存档均正确 |
| M3-02 | 连续使用两次移除服务 | 骰子正确移除，第二次价格按规则上涨 |
| M3-03 | 完成精英战斗 | 难度高于普通战，胜利后稳定获得遗物 |
| M3-04 | 分别使用三种符文 | 目标、次数、槽位和存档正确，不可非法使用 |
| M3-05 | 完成 5 个事件的全部选项 | 前置条件、代价和结果与文案一致 |
| M3-06 | 完成 3 种祭坛结果 | 先验证代价，再应用结果；资源不足不能选择 |
| M3-07 | 使用毒骰跨多个回合 | 叠层、触发、衰减和死亡结算顺序正确 |
| M3-08 | 使用炸弹骰攻击多敌人 | 所有合法目标只受一次伤害，死亡结算正确 |
| M3-09 | 使用金币骰 | 收益立即进入钱包，存档恢复后不重复结算 |
| M3-10 | 分别完成三个验收构筑的整局游戏 | 三种构筑都可通关，核心操作与决策明显不同 |
| M3-11 | 同一地图种子游玩三局并选择不同路线 | 节点和构筑选择产生可观察的战力差异 |
| M3-12 | 导出局内数据 | 文件包含战斗时长、回合、伤害、选择和最终构筑 |

### 6.5 量化通过标准

- M3-01～M3-12 全部通过。
- 三种验收构筑各通关至少 2 次，不能依赖验收模式中途修改数值。
- 任何单一骰子或遗物的选择率不应因明显强度问题达到 100%；如果样本不足，在报告中保留为观察项。
- 5 个事件不能存在一眼可见的无代价最优选项。
- 连续完成 5 局无 S0/S1 缺陷、存档损坏或奖励重复。
- 战斗平均帧率继续满足 M1 标准。

### 6.6 允许遗留

- 内容量仍少于原版。
- 只支持一个职业和一个生物群系。
- 局外解锁、图鉴、成就和完整本地化不在本阶段验收。

## 7. M4：内容扩展与产品化

### 7.1 交付目标

交付一个具备重复游玩、局外成长和基础产品完整度的版本：至少两个职业、两个生物群系、两个 Boss，并具备图鉴、解锁、本地化、完整设置、音频及键鼠/手柄支持。

该阶段回答：**项目是否已经从玩法原型成长为可持续扩充和对外测试的完整游戏版本。**

### 7.2 硬性交付物

- 至少两个完整职业，每个职业至少 4 种专属骰子、3 件专属遗物和独立初始构筑。
- 至少两个生物群系及各自 Boss、敌人池和表现资源。
- 局外存档、图鉴、解锁条件和游戏内成就。
