## ⚠️ 本工程 GUID 双重表征陷阱（v1.1 新增，主理人独立复验，登记为冲刺方案 F32）

> **在动手做任何「按 GUID 找资产 / 判资产是否存在 / 判资产是否被引用」的分析前，必须先读本节。**

- **两套 GUID 并存**：`Assets` 下 233 个带 guid 的 `.meta` 中，**143 个 base64 形态、90 个 hex32 形态**（`.mat` 两种都有：40 base64 ＋ 30 hex32）。
- **形态不同、不可互推**：base64 形态是 **56 字符，解出 41 字节（328 位）** —— 既不是 256 位，**也不是**同一个 128 位值的另一种写法。逐字节比对：`BattleFlow.cs.meta` 的 base64 解码首字节序列为 `5d7217e0…`，与场景引用的 hex `b88ecb60d95a1634aa03daecb10559d0` **不相等**。**两套都是合法 GUID，不能用 base64↔hex 反推。**
- **编辑器内部把两者映射到同一资产**：`Logs/m1-import.log:295` 把 hex `b88ecb60d95a1634aa03daecb10559d0` 当作 `BattleFlow.cs` 的规范 GUID 导入。
- **控制实验（决定性地否定「文本比对法」）**：已知真实资产 `f4fa9e0b…`（牌桌 prefab，场景引用 104 次）与 `36b46978…`（`Desktop_Wooden.mat`）在导入日志里**也是 0 行**。
  ⇒ 「日志里有 ⇒ 该 guid 是真资产」**正向成立**；「日志里没有 ⇒ 资产不存在」**反向不成立**。
  ⇒ **禁止用「guid 字符串在 `.meta` 里找不到」推断「资产缺失」**。反例：`da333294…`、`5c8b75a6…` 在**所有日志里都是 0 行**，但它们对应的 `.cs`（`DemoCDiceRuntime.cs` / `DemoCFallDetector.cs`）**确实存在于 `Assets/Scripts/DemoC/`**。

**强制约束（行动，务必遵守）**

1. **严禁**任何脚本/工具"规范化"、重写或统一 `Assets/**` 下 `.meta` 的 `guid` 字段（后果：场景/预制体引用失效）。
2. **禁止**用 GUID 文本比对来断言「资产未被引用 / 不存在」；判定资产是否进包，**只能用产物侧证据**（`Library/LastBuild.buildreport`、包内字符串检索、`weixinMiniGameAnalyzeBuildSize`）。
3. 任何按 GUID 索引的自动化（含未来的 link.xml 生成器）**必须同时处理 hex32 与 base64 两种形态**，并以后端映射为准。
4. 映射规则本身**仍未确证**（见 §7.3 U5）：**不要试图反推**，遵守上述约束即可。

## 0. 一页摘要

**结论（3 句话）**

1. **同意主理人的大方向**：本工程的**美术载荷确实很小**，可裁的都是零头，真正的量级在 **IL2CPP/WASM 引擎 + .NET 运行时**。我实测的 `Assets/Resources/` 全部非 meta 载荷只有 **282,582 字节（≈276 KB）**（`du -ab`，见 §1.4），不存在「隐藏的 40MB 泄漏点」。
2. **但真正的风险不在「主包 ≤4MB」，而在「总量 ≤30MB」**。一个含 3D PhysX + IMGUI + 旧输入系统的团结 2022 WebGL IL2CPP 包，wasm 落在 15–25MB（压缩后）是常态——它离 30MB 很近。**收缩工作的 KPI 应是「把总量压到 30MB 以内」，4MB 主包靠分包结构达成，与压缩无关**（这点我完全同意主理人 §14.4 的结构判断）。
3. **我新增的杠杆（v1.1 修订后）**：① `DiceMergeGame.cs` 是 `RuntimeInitializeOnLoadMethod` **保根**——它把整块死代码焊在包里，link.xml 救不了它，**只能删源码**；它是 `com.unity.modules.physics2d` 的**决定性编译面锚点**（场景数据删不掉它），**要释放该模块，必须把 `DiceMergeGame.cs`（连同 `DemoCDiceRuntime.cs`）移出编译面**（v1.1 从"场景组件锚"更正为"编译面代码锚"，见 §1.7-B）；② `stripBuiltinResources:0` 与 `m_SlimFeaturesWeixinMiniGame` 是 `ProjectSettings.asset` 里未被 §6 清单覆盖的真开关。**⚠️ 本工程存在 GUID 双重表征陷阱，动手前必读文首专节（F32）。**

**我反对的一条**（详见 §8）：`冲刺方案 §6 B2` 写的「剔除 DemoA/B/C 未引用资产」**不能按目录删**——`BattleM1.unity` 对 `DemoA`（牌桌 prefab）与 `DemoB`（骰子网格/材质）有**活引用**，对 `DemoC` 有两个组件引用。

**四个待用户/实测确认的关键未知数**（详见 §7，绝不写成结论）：
wasm 真实体积、`m_SlimFeaturesWeixinMiniGame` 各字段语义、压缩格式的数值映射、团结转换器里「分包」选项的确切名称。

### 1.1 源码清单与「会被 IL2CPP 裁剪误伤」的逐条枚举

程序集归属见 §1.3。**结论先行：本工程几乎没有反射式访问，裁剪风险面极低。**

| 位置 | 代码 | 性质 | 判定 |

| `BattleFlow.cs:289` | `Enum.GetValues(typeof(AcceptanceScenario))`、`Enum.GetValues(typeof(DiceKind))` | 枚举反射 | **唯一的反射**。`typeof(X)` 已构成对类型的静态引用，IL2CPP 会保留该枚举；且数组遍历仅用于「F10 验收面板」按钮，小游戏不可达（`_input.DebugTogglePressed` 在 `TouchInputSource.cs:22` 恒 `false`） |

#### (e) 输入 / 生命周期实现类是否会被裁掉

- ⇒ 小游戏构建里，**只有 `TouchInputSource` / `MiniGameAppLifecycle` 会被静态引用**（编译期 `#else` 分支被剔除），`DesktopInputSource` / `DesktopAppLifecycle` 无引用 → 可被裁掉。**这是无害的**，但意味着：
  - 不要天真地在 link.xml 里写 `<assembly fullname="DiceDemo.Runtime"><type … preserve="all"/></assembly>`——那会把 4 个实现全保住（虽小，但违背「能裁就裁」）。
  - 注意 `TouchInputSource.cs` / `DesktopInputSource.cs` **本身没有 `#if`**，两个类都会被编译进 `DiceDemo.Runtime.dll`；`#if` 只决定谁被 `new`。这是小游戏侧裁剪能生效的前提。

### 1.7 意外发现（本次调研新增，主理人清单未覆盖）

**A. `DiceMergeGame.cs` 是 `RuntimeInitializeOnLoadMethod` 保根 —— link.xml 救不了它，只能删源码。**

**⚠️ 更正（v1.1）**：v1.0 我写「这两个组件锚住 `Physics2D` + `ScreenCapture` 两个引擎模块」——**该机制推导是错的**。主理人对 `BattleM1.unity` 的组件普查显示：场景内 **`Rigidbody2D`=0、`CircleCollider2D`=0、`BoxCollider2D`=0、`SpriteRenderer`=0**（仅有 6 个 3D `BoxCollider`、1 个 3D `Rigidbody`、81 `MeshRenderer`、54 `TextMesh`、167 `GameObject`/`Transform`）。**场景序列化数据里根本没有 2D 物理组件**，故「场景组件锚 Physics2D」不成立——引擎模块是否入包由**编译面（会被编进包且不会被裁的代码）**决定，不由场景数据决定。

**真正的锚（编译面代码）**：

| 锚点 | 程序集 | 代码 | 能否被裁 | 影响的模块 |
|---|---|---|---|---|
| `DiceMergeGame.cs:51/120/215/225` | `DiceDemo.Runtime` | `AddComponent<Rigidbody2D / BoxCollider2D / CircleCollider2D>()` | **否**：`:39-46` 的 `[RuntimeInitializeOnLoadMethod]` **保根**，IL2CPP 裁不掉 | `com.unity.modules.physics2d` |

## 3. 设置变更规格表

### 3.0 `managedStrippingLevel` 的建议档位（明确回答）

**建议值：`3`（High）**，并配套落地 §2 的 `Assets/link.xml`。

**理由（逐条）**
1. **裁剪风险面已被逐条枚举并排除**：全工程无 `System.Reflection` / `Activator` / `GetMethod|Field|Property` / `MakeGenericType` / `JsonUtility` / `Convert.ChangeType`（§1.1a **实测** 0 命中）；唯一反射是 `Enum.GetValues(typeof(...))`，`typeof` 已构成静态引用，且该面板在小游戏不可达。
2. **只有 1 个构建场景**，且场景内 4 个脚本组件全部可达或由场景保根（§1.5）。
3. IL2CPP 下，`Low`(1) 只做类库级最小精简；`Medium`(2) 与 `Low` 差异有限；**只有 `High`(3) 才会对用户程序集/引擎程序集做激进精简**——本工程恰好是"无反射"的理想对象，**收益最大、代价≈0**。
4. **回退路径明确**：构建后跑 §6 冒烟；若出现 `MissingMethodException` / 缺类型 / 玩法异常，**回退到 `2`（Medium）**，并据 `weixinMiniGameInjectStrippedMethodLogger:1`（§3.1 第 13 项）定位被裁点后再决定。

> 结论一句话：**先 High（3），link.xml 兜底，实测不过再退 Medium（2）**。不选 Medium 起步的理由是——本工程"没有反射"这个前提是**硬事实**（实测 0 命中），没必要为不存在的东西预留档位。

## 5. WXSDK 裁剪风险的处置方案

### 5.1 风险评估（对**本工程**）

**【实测】** 全 `Assets/**/*.cs` 检索 `WXSDK` / `WX.` / `WeixinMiniGame` API 调用：**除 `Assets/Editor/WeixinMiniGameBuild.cs` 的注释与 `Enum.Parse("WeixinMiniGame")` 外，0 处运行时代码引用 WXSDK**。

⇒ **风险成立**：按冲刺方案 `F23` 引述的官方 FAQ，若游戏代码从未使用 WXSDK 任何 Runtime 能力，团结导出时会**裁掉微信 Runtime**，导致开发者工具报错。**本工程正处在这个状态**。

### 5.2 处置：最小、可控、不污染其它平台

**做法**：新增**一个**文件，把引用**全部**关进 `#if UNITY_WEIXINMINIGAME`，并让它在启动时被触碰一次。

```csharp
// Assets/Scripts/Runtime/Platform/WeixinSdkBootstrap.cs   （建议路径，当前不存在）
using UnityEngine;

namespace DiceDemo.M1
{
    /// <summary>
    /// 目的：显式引用一次 WXSDK 的 Runtime 能力，防止团结导出时把微信 Runtime 裁掉
    ///      （官方 FAQ，见冲刺方案 F23）。所有平台专有代码都在 #if 内，非小游戏平台编译为空。
    /// </summary>
    internal static class WeixinSdkBootstrap
    {
        [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.BeforeSceneLoad)]
        private static void Touch()
        {
#if UNITY_WEIXINMINIGAME && !UNITY_EDITOR
            // 只调用一个"幂等、无副作用、必存在"的运行时能力即可。
            // ⚠️ 具体 WXSDK C# API 名称尚未确证（§7-U6）：请先用反编译/反射列出
            //     PlaybackEngines/WeixinMiniGameSupport/Managed/UnityEngine.WeixinMiniGameModule.dll
            //     的公开类型，再填入真实调用。切勿照抄本文档的占位写法。
            UnityEngine.WeixinMiniGame.WX.???();   // ← 占位：待确证 API 后替换
#endif
        }
    }
}
```

**要点**
1. **只引用一次、只碰一个幂等能力**（如取环境/系统信息），不要把业务逻辑挂上去。
2. **必须**放在 `#if UNITY_WEIXINMINIGAME` 内 —— 该宏**仅**在小游戏目标定义（`冲刺方案 F28`），因此 Windows/编辑器构建编译为空，**零污染**。
   - **不要**用 `UNITY_WEBGL` 作条件：webgl 目标也会定义它，会误伤纯 WebGL 构建。
3. 若 `weixinMiniGamePreserveEventDelegate:0`（`:1332`）导致回调被裁，与本方案不冲突（本方案不注册事件）。
4. **待实测**：也请检查 `WeixinMiniGameSupport` 是否有「强制保留微信 Runtime」的构建选项（存在的话优先用选项，而非代码 hack）——本机未能读取该目录，**未确证**。

## 8. 对主理人判断的审阅（同意 / 保留 / 反对）

| 主理人判断 | 我的态度 | 依据 |
|---|---|---|
| 「资产载荷很小，收缩杠杆全在 IL2CPP/代码侧」 | **同意** | E3：`Resources` 仅 276KB；E13：字体未进包；E12 字体是**源体积**不是包内体积 |
| 「主包 ≤4MB 靠分包/结构达成，真正硬约束是总量 ≤30MB」 | **同意，并强化** | §4.4；且提醒"30MB 也尚未被证明" |
| 「`managedStrippingLevel` Low→High 是第一优先级」 | **同意**，档位**明确取 `3`(High)** | §3.0 |
| 「剔除 DemoA/B/C 未引用资产」(`§6 B2`) | **反对/修正** | E4/E6：场景对 DemoA（牌桌）、DemoB（骰子网格材质）有**活引用**，对 DemoC 有两个**组件**引用（⇒ `DiceDemo.DemoC` 程序集被引用）。**不能按目录删**，只能删"未被引用到的子集"（如 `Resources/DiceDemo/*`、孤儿贴图）；**且"修复材质"两套（`DemoB/Generated` vs `DemoC/Generated`）哪套进包须由产物侧确认（§3.2 E）** |
| 「剔除 `DiceMergeGame.cs`」(`§6 B2`) | **同意，且升级为最高优先的代码级动作** | E7：它是 `RuntimeInitializeOnLoadMethod` 保根；link.xml 保不了它，**只能删源码**（§1.7-A） |
| 「包体大头是引擎 + WASM + 托管运行时」 | **基本同意，需细化** | wasm 里的大头通常是**引擎模块 + .NET 运行时/全球化**；本工程可裁模块少——`Physics2D` 被**保根的 `DiceMergeGame.cs`** 锚住、`ScreenCapture` 被 `DemoCDiceRuntime.cs` 锚住（E8；**v1.1 更正：锚点是编译面代码，不是场景组件**），故能动引擎模块的结构杠杆是 **§3.2 A（删 `DiceMergeGame.cs`）+ B（去 `DemoCDiceRuntime.cs`）**；**只删场景组件对 `Physics2D` 无收益** |
| 「沙箱构建不可行，交用户终端」 | **同意**（不挑战，且本任务亦禁止构建） | 本方案所有"待实测"项都因此只能由用户终端的构建回答 |

**一句话总结我的立场**：主理人的方向对，**但把"美术侧已无油水"这一步推到了"那我们就只剩 IL2CPP 托管层"——中间漏了一块半**：① `DiceMergeGame.cs` 这条被保根的死代码链（**主杠杆，编译面锚点**）；② `DemoC` 残留——但**真实机制是 `DemoCDiceRuntime.cs` 的编译面引用，而非"场景组件"**（v1.1 更正：**删场景组件本身对 `Physics2D` ≈ 0 收益**，必须去**编译面**）。**把这两条编译面清理做到位，是把 30MB 线从"危险"拉回"安全"的关键，且都在本任务的可交付范围内。**
