## 4. 产物判读（这是 A1 的真正产出）

脚本会打印每个子目录的字节数与 MB，并提示 4MB / 30MB 两条线。判读规则：

| 观察 | 结论 |
|---|---|
| **`wasm` 文件本身 > 4MB** | **必然如此，且不是问题** —— 微信官方口径「单个分包大小不限」，且 wasm 本就不该待在主包。走「wasm → 分包 / CDN」即可 |
| 总量 ≤ 30MB | ✅ 总量达标 → 可行 |
| 总量 > 30MB | ⚠️ 触发 §6 调优清单（压缩 / 裁剪 / 资源） |
| 根目录有 `game.js` / `game.json` / `project.config.json` | ✅ 转换成功，可直接拖进微信开发者工具 |
| 没有 `game.json` | ❌ 转换链没跑完，回日志找 `WeixinMiniGamePlayerBuildProgram` 相关行 |

### 想更深一层

```cmd
dir /s "D:\NewOne\Client-Dice\Builds\WxMiniGame"
:: 若已装微信开发者工具，直接导入 Builds\WxMiniGame 看真实分包体积与报错
```

> **结构上的一句话结论（先给预期，待实测确认）**：Unity 的 `wasm` 在最好情况下也是 MB 级，**不可能塞进 4MB 主包**。所以 ≤4MB 主包这条线是**靠分包/CDN 结构达成**的，不是靠压缩——真正的硬约束是**总量 ≤30MB**。这也意味着 §9 的「主包 ≤4MB」应重新表述为「主包放引导代码，wasm/data 进分包」。

### 4.1 构建后必查 3 条（缺一条就等于没有结论）

| # | 查什么 | 怎么查 | 判定 |
|---|---|---|---|
| 1 | **托管侧 `UNITY_WEBGL` 是否真的定义** —— 决定触摸是否生效 | **⚠️ 不要检索类型名 `TouchInputSource`（见下方「为什么这个判据是错的」）**。正确判据：读 **IL2CPP 生成 C++** —— `Library\Bee\artifacts\WeixinMiniGame\il2cppOutput\cpp\DiceDemo.Runtime.cpp`，看 `BattleFlow_CreateInputSource` 的函数体 | 函数体是 `il2cpp_codegen_object_new(TouchInputSource_…_il2cpp_TypeInfo_var)` + `TouchInputSource__ctor(…)` ⇒ **宏已定义 ✅**（2026-09-18 实测确认）<br>若函数体是 `DesktopInputSource…` ⇒ 触摸路径被编译掉，属 **P0**，需回改 `IInputSource` 选择逻辑 |
| 2 | **骰子材质是否真的进包**（防洋红退化） | 在产物里检索字符串 `阶段丙修复` | 命中 **19** 条（`Die Border 1..9`、`Die One Side 1..9`、`Die Outline`）⇒ 材质链完整 ✅<br>**0 条 ⇒ P0** |
| 3 | **总量 / 主包两条线** | §4 的体积拆解 | 总量 ≤30MB ✅；主包 ≤4MB 由分包/CDN 结构达成 |

> **为什么第 1 条必须查**：我们手上唯一的 `UNITY_WEBGL` 证据是 `WeixinMiniGamePlayerBuildProgram.exe` 的字符串表，
> 上下文里带 `/cpp` ⇒ 那是**原生（C++/IL2CPP 侧）**的宏定义集。**原生侧有宏 ≠ 托管侧有宏**，而 `#if` 是在**托管侧**求值的。
> 所以这条只能由产物判定。完整推理见 `微信小游戏平台可行性冲刺方案.md` **§16.5**。

> **⚠️ 为什么旧判据「检索类型名 `TouchInputSource`」是错的（v1.3 修正，重要）**：
> `Assets/Scripts/Runtime/Input/TouchInputSource.cs` 整个文件**没有任何 `#if` 守卫**（见该文件全文，`public sealed class TouchInputSource : IInputSource` 无条件编译）。
> 因此**无论宏有没有定义，`TouchInputSource` 这个类型名都会进程序集、也会出现在产物/元数据里** —— 用它当判据**永远为"出现"，永远假通过**。
> 同理 `DesktopInputSource` 也总会存在。**能不能区分宏，取决于「调用点」而不是「类型是否存在」**：
> `BattleFlow.CreateInputSource()`（`BattleFlow.cs:65-72`）的 `#if UNITY_WEBGL && !UNITY_EDITOR` 分支里 `return new TouchInputSource();` ——
> **只有被选中的那一支才会被编译进方法体**。所以要看 `CreateInputSource` / `CreateAppLifecycle` 的函数体，而不是全局搜字符串。
> IL2CPP 生成的 C++ 是这条链上最直接、可读、可复核的证据（`Library\Bee\artifacts\<Target>\il2cppOutput\cpp\DiceDemo.Runtime.cpp`）。

> 参考：Windows 版 M1 产物里**没有** `TouchInputSource`（因为桌面走 `DesktopInputSource`），
> 但这**不能**用来外推小游戏目标（F34）。

## 10. 出真实小游戏包的正确流程（v1.4 新增 · **必读**）

### 10.1 结论先行

本手册 §0 的「第 2 步 构建」**只完成了一半**：它产出的 `Builds\WxMiniGame` 是
**Tuanjie WebGL 播放器产物**（用的是 WebGL 默认 `Default` 模板），**不是微信小游戏包**：

| 判据 | 实测 |
|---|---|
| 产物根目录有 `game.js` / `game.json` / `project.config.json` 吗 | **三者皆无** ❌ |
| 产物 `TemplateData\` 与模块 `…\WeixinMiniGameSupport\BuildTools\WebGLTemplates\Default\TemplateData\` | **文件集完全一致** |

### 11.1 坑 (a) · `AssetBundle` / 模块裁剪坑【根因 · 已验证】

- **现象**：`WXBase.cs(884,34): error CS0103: The name 'AssetBundle' does not exist in the current context`。
- **机理**【已验证】：
  - `Packages/manifest.json` 被裁到只剩 animation/audio/imageconversion/imgui/jsonserialize/physics/physics2d/screencapture/ui，**没有** `com.unity.modules.assetbundle`；
  - SDK 的 `Library/PackageCache/com.qq.weixin.minigame@…/Runtime/WXBase.cs:884` 用了 `AssetBundle.LoadFromMemory(abBytes)`；
  - SDK `package.json` 写的是 `"dependencies":{}` ⇒ **不会**自动补回该模块；
  - 连坐：`Runtime/WxWasmSDKRuntime.asmdef`（name `Wx`，含编辑器）编译失败 ⇒ 引用它的 `Editor/WxWasmSDKEditor.asmdef`（name `WxEditor`）也失败 ⇒ SDK 的**微信子平台不注册**（`WeixinSubplatformInterface.cs:19` 的 `RegisterSubplatform` 不执行）。
  - **连坐实锤**：`Library/ScriptAssemblies/` 实测 **38 个文件里没有 `Wx.dll`、也没有 `WxEditor.dll`**；其余程序集（`DiceDemo.*`、`FindReference2.Editor`、`UnityTcp.*` 等）**全在** ⇒ `Wx` 没产出程序集，`WxEditor` 因此编不出来。
- **修复（GUI）**：`Window → Package Manager` → 左上 **`+`** → **`Add package by name…`** → Name 填 `com.unity.modules.assetbundle`（Version 留空）→ **`Add`**。
  - **备选**：手改 `Packages/manifest.json` 加 `"com.unity.modules.assetbundle": "1.0.0",`（推荐仍走 Package Manager）。
- **期望（三条同时满足才算成功）**：① Console 不再报该 CS0103；② Package Manager `In Project` 里能看到 **Asset Bundle**；③ **`Library/ScriptAssemblies/` 下新出现 `Wx.dll` + `WxEditor.dll`**（装前实测这两个文件不存在）—— 这是"第 1 步生效"的直接判据。
- ⚠️ **结论**：为压体积裁模块时，`assetbundle` 是**小游戏目标的硬依赖**，**不能裁**。

### 11.2 坑 (b) · `Assets/WX-WASM-SDK-V2/` 陈旧路径坑 + SDK 两种引入模式【已验证】

- **现象**：`Failed to load ScriptableObject at path: Assets/WX-WASM-SDK-V2/Editor/MiniGameConfig.asset`（×2）→ `ArgumentNullException: Value cannot be null. Parameter name: objectToOverwrite`，栈 `JsonUtility.FromJsonOverwrite ← DefaultWeChatMiniGameSettings.ApplySettings ← DefaultWeChatBuildProfileHelper.Build`。
- **机理**【已验证】：
  - 引擎 `UnityEditor.CoreModule.dll` 内**硬编码**了 `Assets/WX-WASM-SDK-V2/Editor/MiniGameConfig.asset`、`.../PlayableConfig.asset`、`.../Runtime/wechat-default/images/...`（UTF-16 串），并含 `DefaultWeChatBuildProfileHelper`/`DefaultWeChatMiniGameSettings`/`ApplySettings`/`objectToOverwrite`；
  - 即引擎**内置的** WeChat 设置只在 **Assets 插件模式**下能找到配置资产；
  - 本工程是 **Package 模式**（SDK 在 `Library/PackageCache/…`，`Assets/` 下**无** `WX-WASM-SDK-V2/`）⇒ 加载失败 ⇒ 目标对象 `null` ⇒ 崩。
- **SDK 两种引入模式**【已验证】`Editor/wx-editor.xml:322-334`：
  - `UnityUtil.GetWXSDKRootPath()`：Unity 版 → `.../Assets/WX-WASM-SDK-V2`；Tuanjie **导入插件模式** → 同样 `.../Assets/WX-WASM-SDK-V2`；Tuanjie **Package 模式** → 插件的真实路径（如 `.../PackageCache/com.qq.weixin.minigame@…`）。
  - `UnityUtil.GetSDKMode()` → `SDKMode.Assets`（资源目录模式）/ `SDKMode.Package`（包模式）。
- **修复**：见 11.3+(d)。**不要**为了消掉这条报错去手建 `Assets/WX-WASM-SDK-V2/`——SDK 的转换器（`WXConvertCore.cs:394/466/591/625/2393` 的 `if (GetSDKMode()==Package)`）本就支持 Package 模式；问题在"引擎内置 helper 只认 Assets 路径"，解决之道是**别让它跑**。
- **附**【已验证】：SDK 自身也有一处同款默认值 `Editor/WXConvertCore.cs:93 defaultImgSrc = "Assets/WX-WASM-SDK-V2/Runtime/wechat-default/images/background.jpg"`，Package 模式下会被替换/忽略，**不是**必须建目录的理由。

### 11.3 坑 (c) · BuildPath 为空【已验证】

- **现象**：`New WeChat Profile: 的打包路径 "" 无效，请重新设置 BuildPath`（注意 profile 名 `New WeChat Profile` 与磁盘上的 `MiniGameProfile` **不一致** ⇒ 被构建的是**新建未保存、未填路径**的 profile）。

### 11.4 坑 (d) · 子平台必须选 SDK 的 `WeChat:微信小游戏`【规则 · 已验证】

> ⚠️ **顺序陷阱（最要紧，先读）**：装回 `assetbundle`（11.1）**之前**，Sub Platforms 下拉里**根本不会出现 `WeChat:微信小游戏`** —— 只有一个引擎内置的「微信小游戏」。因为 `WxEditor` 从未编译成功（见 11.1 的 `ScriptAssemblies` 实锤），`WeixinSubTargetManager` 的 `[InitializeOnLoad]` 从未执行、`RegisterSubplatform` 从未被调用。
> **所以必须：① 先装 `com.unity.modules.assetbundle` → ② 等重编译、确认 `Wx.dll`/`WxEditor.dll` 已产出且 CS0103 消失 → ③ 这时下拉里才会新出现 `WeChat:微信小游戏`，再选它 → ④ 填非空 BuildPath → Build。**
> **`WeChat:微信小游戏` 的出现本身就是「11.1 修复生效」的第一个信号；它出现之前去找它 = 找不到，这是预期行为，不是菜单写错。**

> **规则：`File → Build Settings → MiniGame → Sub Platforms` 里，必须选由 SDK 提供的那一项（显示名含 `WeChat:微信小游戏`），不能选引擎内置的 `微信小游戏`。**

- **为什么**【已验证】：
  - SDK 的子平台名是字面量：`Editor/BuildProfile/WeixinSubplatformInterface.cs:37-40` `GetSubplatformName() => "WeChat:微信小游戏"`；
  - **选 SDK 子平台** ⇒ 走 `WeixinSubplatformInterface.Build`（`:53-96`）⇒ **全程不调用** `DefaultWeChatMiniGameSettings.ApplySettings`；它自己做 `WechatBuildPreprocess`（`:200-239`，设模板 `Packages/com.qq.weixin.minigame/WebGLTemplates/WXTemplate2022TJ`、压缩 `Disabled`、linker `Wasm`）+ `CallDoExport`（`:241-263`）→ `WXConvertCore.DoExport()`；即便 profile 仍是内置设置类型，SDK 也在 `:124-132` 兼容它。
  - **选引擎内置** ⇒ 走 `DefaultWeChatBuildProfileHelper.Build` ⇒ `ApplySettings` ⇒ 撞 11.2 的路径墙。
- **为什么内置设置类型一直没被自动纠正**【已验证】：`Editor/BuildProfile/WeixinBuildProfileUpdater.cs:1` 被 `#if TUANJIE_1_6_OR_NEWER && !TUANJIE_1_8_OR_NEWER` 包住 ⇒ **1.10.2 不编译** ⇒ 不会自动把 `DefaultWeChatMiniGameSettings` 换成 `WeixinMiniGameSettings`。
- **修复（GUI）**：先做 11.1（装回 assetbundle，否则 SDK 子平台**不出现**）→ 在 Sub Platforms 选 **`WeChat:微信小游戏`** → 点 **`Add Build Profile`** 新建 profile（应绑 SDK 设置）→ 填 **Build Path** → 配 **project conf**（`微信小游戏转换平台 → 更多配置项` / `扩展菜单 → debug`）→ 勾选 → **Build**。
- **期望**：产物根目录出现 **`game.js` + `game.json` + `project.config.json`**（+ `wasmcode/`、`data-package/`）。反查【已验证】：`WXConvertCore.cs:83 defaultTemplateDir=wechat-default`；`:1543/:2286` 落盘清单含上述三件；模板源 `Runtime/wechat-default/{game.js,game.json,project.config.json}` 就在包内。
