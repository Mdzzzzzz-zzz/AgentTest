## 1. 目标与范围

用现有 M1.1 三维战斗切片，打通「团结引擎 → 微信小游戏」的构建与运行链路，尽早暴露平台风险。

**范围内**：构建链路、渲染栈规范化、输入抽象、包体收缩、竖屏适配、真机性能采集。
**范围外**：M2～M4 玩法内容（地图/遗物/商店）、正式 UI 视觉、音频、Live Ops。

本阶段**不追求可发布**，只回答三个问题：

1. 能不能转？
2. 包体能不能压进上限？
3. 3D 物理在真机能不能达到可玩帧率？

## 3. 关键修正（本轮推翻/修正的判断）

1. **「CJK 字体没进包」→ 转折 → 最终回归「确实没进包」（本条经历了两轮翻转，以第二轮为准）**。第一轮：美术侧依「HUD 是 IMGUI」推断四套 CJK 字体未进包，技术侧追出 `BattleM1 → Desk Base - Forest.prefab → Jersey10 SDF → NotoSans SDF fallback → TTF` 的引用链，据此推翻。第二轮（**当前结论**）：包内字符串检索＋字节账目**实测**证明 5 套 NotoSans 与全部 `.ttf` **0 命中、确实未进包**（F20），引用链存在但未被收集（F21）。⇒ 原判断「字体是真实可压缩的大头」**不成立**，实际字体载荷约 1MB。
   > 方法论：**「依赖链存在」与「资源进包」是两个独立命题，必须以包内实测为准。**
2. **「当前是 URP 工程」不成立。** 当前是 Built-in RP；「规范化到 URP」是**主动改造**，而非修复既有 URP 配置。原「URP 黑屏」风险随之下调。
3. **色彩空间与朝向确认需改**：Linear → Gamma；AutoRotation → Portrait。
4. **渲染管线路线待复核**：两位成员复核后一致**建议保持 Built-in**（不引入 URP；竖屏 UI 用 uGUI Text + 子集化 TTF），与此前用户所选「规范化到 URP」冲突。
   补充事实：**两条路线都必须重做材质**——当前材质挂的是 AssetRipper 导出的 URP shader 副本（F4），其在本工程内可用性本身待验证。因此「保持 Built-in」的省事程度低于表面，需用户最终拍板。
5. **「A-1 编译未验证」已被证伪为「已通过」。** 编辑器日志中的 4 条 `CS0246: 'IInputSource'/'IAppLifecycle' could not be found` 是**在编辑器开着的情况下写文件的瞬态首轮错误**——Unity 先导入 `BattleFlow.cs`（引用新接口）再导入 `Input/*.cs`，首轮必然失败；Tundra 随后 `1 items updated` 自动重跑第二轮并 **build success**。时序佐证：Input 六文件 `17:24:40–17:24:58` → `BattleFlow.cs 17:25:35` → `DiceDemo.Runtime.dll 17:27:25`（重编成功）。**结论：A-1 无需任何修补**；唯一遗留是既有告警 `CS0414: BattleFlow._debugGold 已赋值但未使用`（非本轮引入，可随手清理）。
   > 方法论沉淀：**在编辑器打开状态下改脚本，日志里出现一轮 CS 错误属正常现象，必须以「最终 Tundra build 结果 + 产物 mtime」为准，不可据首轮报错误判失败。**

6. **⚠️ 新增：本项目存在「GUID 双重表征陷阱」，已推翻至少 5 处既有判断（F32）。**
   本工程的资产 GUID 有 **hex32** 与 **base64（解出 41 字节）两套并行写法**，且**文本不可互推**（`BattleFlow.cs.meta` 写 base64、场景引用写 hex，二者文本与 base64 解码皆不相等，但编辑器内部映射到同一资产）。
   ⇒ **铁律：禁止用「guid 字符串在 `.meta` 里找不到」推断「资产缺失」。**
   ⇒ 据此作废/撤回的判断：**§10「骰子缺材质 P0」**（实为假警报，19 个修复材质已正确绑定并进包，F26/F33）、**§11-7**、**§11-8**、**F5**、**F16**（后两条的「缺失」部分撤回为「未确认」）。
   > 方法论沉淀：**本项目任何涉及 GUID 的结论，都必须用「目标产物内实测」（如包内字符串检索／构建报告清单）来定论，不可用源文件文本比对。**

## 15. 2026-09-16 二次复核：GUID 双重表征陷阱与 P0 结案

### 15.1 起因

### 15.2 证伪链

| 1 | `BattleFlow.cs.meta` 的 `guid:` 是 base64 `XXIX4Hn/VXtwzeBCVgk8OdSeBlKduNwNOBr94CoWA/sVgg4pTyT5D4s=`（56 字符） | 解出 **41 字节**，不是 16 字节 |

| 3 | 把 step 1 解码成 hex 得 `5d7217e0…`，**逐字节比对也不等于** `b88ecb60…` | ⇒ base64 不是「同一 128 位值的另一种写法」 |
